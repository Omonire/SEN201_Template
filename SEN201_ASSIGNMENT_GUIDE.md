# SEN 201 Software Engineering Assignment Guide

A general guide to the SEN 201 Software Engineering assignment. It explains the common
assignment structure and gives a neutral overview of all seven SDLC models so that a
model can be chosen and justified for any case study. No student-specific information
is included.

## Purpose

The assignment tests whether a software engineering process model can be explained
clearly, compared with alternatives and applied convincingly to a case study. The aim
is to connect the characteristics of a model to the facts of a project, not to reproduce
textbook definitions.

## Common assignment structure

| Section | What it should do |
|---|---|
| Introduction | Establish why process models matter in software engineering |
| Definition of a Software Engineering Model | Explain abstraction and what a process model represents |
| Overview of SDLC Models | Compare the available models before choosing one |
| Selected Model | Describe the chosen model accurately, including its phases or cycles |
| Case Study | Report only the facts given in the brief |
| Application | Walk through the model using the case |
| Justification | Connect model characteristics to case facts |
| Advantages | Explain benefits with project-specific consequences |
| Structural Diagram | Explain the diagram and insert the screenshot |
| Disadvantages | Explain limitations and how they would be managed |
| Conclusion | Synthesise without introducing new material |
| References | Cite credible sources in APA 7th edition |

## SDLC models

### 1. Waterfall Model

A linear sequential process in which each phase is completed and signed off before the
next begins: requirements, design, implementation, integration and testing, deployment,
and operation and maintenance. It suits stable requirements, fixed deadlines and a high
cost of error. Its weaknesses are late defect discovery, expensive change and deferred
stakeholder feedback.

### 2. V-Model (Verification and Validation)

An extension of the phase idea in which every development activity is paired with a
corresponding testing activity. Verification checks that the product is being built
correctly; validation checks that the right product is being built. It suits projects
where quality assurance and traceability are critical, but it is rigid and changes late
in the cycle are costly.

### 3. Spiral Model

A risk-driven model that repeats four activities in cycles: determine objectives,
identify and resolve risks, develop and test, then plan the next iteration. Each loop
produces a more complete version of the system. It suits large, high-risk or uncertain
projects, but requires risk-analysis expertise and can be expensive.

### 4. Prototype Model

A working example is built quickly so that stakeholders can inspect it and give
feedback, after which the requirements are refined. It suits unclear or evolving user
needs. The risk is that stakeholders treat the prototype as the final product or that
poor-quality prototype code is carried into the real system.

### 5. Agile Model

An iterative and incremental approach built around short cycles, frequent delivery of
working software, close stakeholder collaboration and adaptation to change. It suits
projects where requirements are likely to evolve and users can give continuous feedback.
It is weaker where regulation fixes the requirements early or where heavy documentation
and formal sign-off are required.

### 6. Incremental Model

The system is divided into functional slices that are built and delivered one after
another. Each increment adds capability to the previous one. It suits projects where a
usable core is needed early or where delivery can be staged. It requires good interface
design, and the overall architecture must be planned before increments begin.

### 7. Iterative Model

A single capability or the whole system is refined through repeated versions. Each
iteration improves on the last based on evaluation and feedback. It suits projects where
the final solution is not fully understood at the start. It needs careful version
control and can suffer from scope creep if iterations are not controlled.

## Choosing a model

Models are not mutually exclusive; large systems often combine elements of several.
A defensible choice considers:

- stability and clarity of requirements;
- cost and consequences of error;
- need for early working software or stakeholder feedback;
- level of risk and uncertainty;
- regulatory, audit and documentation obligations;
- fixed or flexible cost and schedule constraints.

## Case study discipline

Use only the facts in the brief: requirements, objectives, stakeholders and expected
outcomes. Do not invent evidence. Show how the chosen model handles those facts, and
explain any controls needed for its weaknesses.

## Structural diagram

Draw a diagram appropriate to the selected model in draw.io at
<https://app.diagrams.net/>. For example, a Waterfall assignment uses a phase cascade
with sign-off gates, while a Spiral assignment uses repeating risk-driven cycles. Create
it manually, verify it before submission and insert the screenshot in the main
assignment.

## Research and referencing

Use textbooks, peer-reviewed publications, university resources and official
documentation. Verify titles, authors, dates and URLs, and never invent publications,
DOIs or links. Distinguish established facts from interpretation. Cite sources in-text
and provide an APA 7th edition reference list.

## Deliverables

- **Main assignment** — the submitted academic document.
- **Explanation guide** — a companion explaining section meanings, terminology,
  diagram interpretation and likely lecturer questions. It complements the assignment
  rather than repeating it.

## Academic integrity

These materials are educational guides, not answer keys. Review, verify and edit all
work before submission, and follow the lecturer's instructions and the institution's
academic integrity policies. Where they conflict with a template, the lecturer wins.
